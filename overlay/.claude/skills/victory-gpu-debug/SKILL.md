# GPU investigation
Follow AGENTS.md. Investigate and build the checked-out private fork, not the public upstream. Use public upstream only for reference. Work on authorized workloads only. Build diag with `cargo build --profile diag -p victory --features diagnostics --locked`. Confirm flags from current README/source. Record exact GPU, driver, wave capabilities, build, resolution and cache state. Use controlled short runs; stop at GPU reset or severe memory pressure. Never change TDR or suppress watchdogs.
For device removal: collect the first HRESULT and DRED breadcrumbs/page-fault metadata with `VICTORY_D3D12_DRED=1`, then correlate queue/list submission, fences, allocator and descriptor/resource lifetime in victory-gpu. Debug layer and GBV are separate diagnostic runs; their overhead is not benchmark evidence. WARP is an isolation test only. For a real compatible .dxdmp, use installed pix-diagnose and DxDmp locally; a DRED log or CPU minidump is not such a file. Report missing dump/tool support honestly.
For black frames: use local capture metadata, identify first incorrect stage from intermediate target to final back buffer; trace state, resource binding, format, copy/resolve, viewport and presentation. Do not send screenshots or shader blobs to the model or remote MCP. Use independent synthetic captures for model-visible evidence. PIX GPU capture analysis may require human UI interaction; timing capture tools do not replace it.
For performance: isolate CPU recording, PSO compilation, memory transfer, submission, GPU execution and present. Use PIX timing/WPR or existing timing diagnostic; distinguish wait from work. Compare like-for-like without validation/diagnostic overhead.
Propose a focused runtime fix supported by an independent synthetic GPU regression. Validate actual content/semantics, not just absence of crashes. Summarize observations, hypotheses ruled out, uncertainty and the next experiment; get approval before editing production code.
